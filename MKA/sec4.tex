\section{Tamarin Model}
\label{sec:model}

\subsection{Cryptographic Primitives and Equational Theory}

Our Tamarin model is built on the following builtins and functions:
\begin{sloppypar}
\begin{itemize}
  \item \textbf{Symmetric encryption/decryption:} We used predefined functions \texttt{senc}/\texttt{sdec} satisfying \texttt{sdec(senc(m,k),k) = m} for symmetric encryption and decryption. The adversary can only decrypt a ciphertext if it knows the corresponding key.
  \item \textbf{Key derivation:} \texttt{kdf(key,label)} is modelled as an uninterpreted two-argument function; no algebraic identities are assumed, which captures the idealised one-way property of a KDF.
  \item \textbf{Message authentication:} Tamarin does not provide a built-in MAC primitive, so we define \texttt{mac(M,K)} and \texttt{macverify(mac(M,K),M,K) = mactrue}; the equation ensures that the adversary can only produce a valid ICV if it knows the ICK.
  \item \textbf{Monotone counters:} We define \texttt{count(x)} to model counter advancement and use it for both MN and KN progression.
  \item \textbf{Message-number generation:} We define a private function \texttt{genMN(\$Party)} that produces a deterministic initial message number for each participant identity. The function is declared \emph{private}, meaning the adversary cannot compute or predict initial MN values. This models the assumption that both participants have already exchanged at least one MKAPDU in a prior discovery phase and maintain private MN state. This abstraction allows our model to focus on the key agreement phase without modeling the full MKA hello/discovery protocol.
\end{itemize}
\end{sloppypar}

\paragraph{Inline restrictions.} Tamarin supports two mechanisms for constraining execution traces: named \texttt{restriction} blocks and inline \texttt{\_restrict} action facts. Our model uses inline \texttt{\_restrict} actions within protocol rules to enforce local validity conditions (e.g., MAC verification, counter monotonicity) directly at the point where they are checked. This approach keeps each rule self-contained and mirrors the sequential checking logic of the actual protocol implementation.

\subsection{Protocol Participants and Long-Term State}

\paragraph{CAK setup.} The rule \texttt{Setup\_CAK} generates a fresh CAK ${\mathit{cak}}$ and stores it as a persistent shared fact \texttt{!SharedCAK(\textasciitilde cak)}, available to both parties.

\paragraph{Derived keys.} Both participants independently compute
\[
  \mathit{kek} = \mathtt{kdf}(\mathit{cak}, \texttt{'KEK'}),\quad
  \mathit{ick} = \mathtt{kdf}(\mathit{cak}, \texttt{'ICK'})
\]
at the beginning of each protocol step, since both parties share the same CAK.

\subsection{Initial Session Rules}

\paragraph{Initial\_KeyServer\_Send.} The Key Server:
\begin{enumerate}
  \item Retrieves \texttt{!SharedCAK(\textasciitilde cak)}.
  \item Generates a fresh Key Number ${\mathit{kn}}$ and a fresh nonce ${\mathit{KS\_nonce0}}$.
  \item Derives $\mathit{sak1} = \mathtt{kdf}(\mathit{cak}, \langle \$\mathit{Keyserver}, {\mathit{kn}},{\mathit{KS\_nonce0}}\rangle)$.
  \item Computes $\mathit{c1} = \mathtt{senc}(\mathit{sak1}, \mathit{kek})$.
  \item Computes $\mathit{icv1} = \mathtt{mac}(\langle \$\mathit{Keyserver}, \mathit{mn\_ks1},{\mathit{kn}}, \mathit{c1}\rangle, \mathit{ick})$.
  \item Sends $\langle \$\mathit{Keyserver}, \mathit{mn\_ks1}, {\mathit{kn}}, \mathit{c1}, \mathit{icv1}\rangle$ and stores \texttt{KSSTATE0}.
\end{enumerate}
The action fact \texttt{SentInitialSAK} is recorded for use in the authentication lemmas.

\paragraph{Initial\_Server\_Receive.} The Server:
\begin{enumerate}
  \item Receives the MKAPDU from the network.
  \item Retrieves \texttt{!SharedCAK(\textasciitilde cak)} and verifies $\mathit{icv1}$ using a \texttt{\_restrict} action: \texttt{macverify(icv1, \ldots, ick) = mactrue}.
  \item Restricts the received MN to match the expected counter: $\mathit{mn\_ks1} = \mathtt{count}(\mathit{mn\_ks})$.
  \item Decrypts the payload: $\mathit{sak1} = \mathtt{sdec}(\mathit{c1}, \mathit{kek})$.
  \item Computes and sends its acknowledgement ICV2.
  \item Records \texttt{ServerAcceptedSAK} and stores \texttt{SSTATE0}.
\end{enumerate}

\paragraph{Initial\_KeyServer\_Confirm.} The Key Server receives the Server's ACK, verifies ICV2, checks that the received MN matches the expected counter, and transitions to \texttt{KSSTATE1}, recording \texttt{InitialSessionCompleted}.

\subsection{Rekey Rules}

The rekey phase mirrors the initial phase structurally, but it reads the previous state (\texttt{KSSTATE1}/\texttt{SSTATE0}) to enforce monotonicity. Specifically:

\begin{itemize}
  \item $\mathit{mn\_ks2} = \mathtt{count}(\mathit{mn\_ks1})$ and $\mathit{kn1} = \mathtt{count}({\mathit{kn}})$ ensure both counters advance.
  \item A fresh nonce ${\mathit{KS\_nonce1}}$ ensures SAK2 is independent of SAK1 even for identical KN paths.
  
\end{itemize}

\subsection{Adversary Model and Compromise Rules}

We model a standard Dolev--Yao adversary augmented with two compromise rules:
\begin{itemize}
  \item \texttt{Reveal\_SAK}: exposes an initial SAK from \texttt{KSSTATE0}; records \texttt{RevealSAK}.
  \item \texttt{Reveal\_CAK}: exposes the CAK from \texttt{!SharedCAK}; records \texttt{RevealCAK}.
\end{itemize}
These rules allow the formulation of conditional security properties, for example that secrecy holds unless the CAK is revealed.

The rule \texttt{Malicious\_KeyServer\_Send} models a Key Server that uses the CAK to construct a well-formed MKAPDU carrying an arbitrary fresh SAK ($\widetilde{\mathit{fakeSAK}}$) instead of a properly KDF-derived one. This rule is used to probe the protocol's acceptance mechanism.

\paragraph{Forward-secrecy limitation.} Because all operational keys (KEK, ICK, SAK) are derived from the single long-term CAK, compromising the CAK at any point enables an adversary to re-derive all past and future sub-keys. The protocol therefore does not provide forward secrecy: a CAK compromise retroactively exposes every session. This is an inherent limitation of pure pre-shared-key architectures without ephemeral key exchange, and it is captured by the conditional form of our secrecy lemmas, which explicitly exclude CAK-reveal traces.

\paragraph{Regarding quantum adversaries.} Our symbolic model abstracts away computational complexity and therefore does not capture brute-force attacks or their quantum speedups (e.g., Grover's algorithm reducing effective symmetric key strength from $2^{128}$ to $2^{64}$ operations). Since all cryptographic primitives in MKA are symmetric, the protocol is not vulnerable to Shor's algorithm. Assessing quantum resilience of the symmetric primitives requires a computational (rather than symbolic) analysis and is outside the scope of this work.

The fourteen Tamarin lemmas defined in our model fall into six functional categories, formalizing the security requirements defined in Section~\ref{sec:requirements}. In Tamarin syntax, temporal markers \texttt{\#i} and \texttt{\#j} denote time points on an execution trace (where \texttt{@i} indicates an event occurring at time \texttt{\#i}), and \texttt{K(m)} denotes the adversary's knowledge of message \texttt{m}. Below, we present the formal specifications and semantic analysis of each lemma group.

\subsubsection{Protocol Executability}
To guarantee that the protocol rules do not contain logical deadlocks or unsatisfiable restrictions, we verify the reachability of a full two-round execution trace.

\paragraph{Executable Lemma (\texttt{executable}).} Formulated as an \texttt{exists-trace} property, this lemma asserts that there exists at least one execution trace where both the initial session and a subsequent rekey round complete successfully:
\begin{align*}
\exists \, \mathit{mn_{ks1}}, \mathit{mn_{s1}}, \mathit{kn}, \mathit{sak1}, \mathit{mn_{ks2}}, \mathit{mn_{s2}}, \mathit{kn1}, \mathit{sak2}, i, j. \\
\mathtt{InitialSessionCompleted}(\mathit{mn_{ks1}},\mathit{mn_{s1}},\mathit{kn},\mathit{sak1})@i \;\land \\
\mathtt{RekeySessionCompleted}(\mathit{mn_{ks2}},\mathit{mn_{s2}},\mathit{kn1},\mathit{sak2})@j
\end{align*}
Tamarin successfully synthesizes a valid trace, proving that the model state facts and counter restrictions permit complete protocol runs under non-adversarial conditions (fulfilling \textbf{SR1}).

\subsubsection{Agreement and Entity Authentication}
Mutual agreement lemmas ensure that both parties share consistent view of session parameters and that no session completes without the active participation of the counterparty.

\paragraph{Initial and Rekey Agreement (\texttt{initial\_agreement}, \texttt{rekey\_agreement}).} These \texttt{all-traces} lemmas enforce injective agreement from the Key Server's perspective. For any trace where an initial (or rekey) session completes at time $i$, the Key Server must have previously initiated and transmitted that exact SAK at an earlier time $j < i$:
\begin{align*}
\forall \, \mathit{mn_{ks1}}, \mathit{mn_{s1}}, \mathit{kn}, \mathit{sak1}, i. \, \mathtt{InitialSessionCompleted}(\mathit{mn_{ks1}},\mathit{mn_{s1}},\mathit{kn},\mathit{sak1})@i \implies \\
(\exists \, j. \, \mathtt{SentInitialSAK}(\mathit{mn_{ks1}},\mathit{kn},\mathit{sak1})@j \land j < i)
\end{align*}

\paragraph{Server Authentication Lemmas.} The lemmas \texttt{server\_}\allowbreak\texttt{authentication\_}\allowbreak\texttt{initial} and \texttt{server\_}\allowbreak\texttt{authentication\_}\allowbreak\texttt{rekey} establish non-injective aliveness of the Server node. Provided that the shared long-term CAK has not been compromised ($\neg \exists \mathit{cak}, k. \, \mathtt{RevealCAK}(\mathit{cak})@k$), the Key Server's completion of an initial or rekey session guarantees that the Server actively validated the MKAPDU and prepared a corresponding acknowledgement ACK at time $j < i$ (fulfilling \textbf{SR2}).

\subsubsection{SAK Confidentiality and Secrecy}
Secrecy lemmas verify that operational SAKs derived during protocol runs remain protected against passive and active Dolev--Yao adversaries.

\paragraph{SAK Secrecy Lemmas.} The secrecy lemmas (\texttt{initial\_}\allowbreak\texttt{sak\_}\allowbreak\texttt{secrecy\_}\allowbreak\texttt{no\_}\allowbreak\texttt{reveal} and \texttt{rekey\_}\allowbreak\texttt{sak\_}\allowbreak\texttt{secrecy\_}\allowbreak\texttt{no\_}\allowbreak\texttt{reveal}) state that if a session completes at time $i$, and neither the session key ($\mathit{sak1}$ or $\mathit{sak2}$) nor the long-term secret ($\mathit{cak}$) has been exposed via adversary reveal rules ($\mathtt{RevealSAK}$ or $\mathtt{RevealCAK}$), then the adversary can never learn or derive the SAK:
\begin{align*}
\forall \, \mathit{mn_{ks1}}, \mathit{mn_{s1}}, \mathit{kn}, \mathit{sak1}, i. \, [ \mathtt{InitialSessionCompleted}(\mathit{mn_{ks1}},\mathit{mn_{s1}},\mathit{kn},\mathit{sak1})@i \land \\
\neg(\exists k. \, \mathtt{RevealSAK}(\mathit{mn_{ks1}},\mathit{mn_{s1}},\mathit{kn},\mathit{sak1})@k) \land \neg(\exists \mathit{cak}, l. \, \mathtt{RevealCAK}(\mathit{cak})@l) ] \implies \\
\neg(\exists m. \, \mathbf{K}(\mathit{sak1})@m)
\end{align*}
Both secrecy lemmas hold, proving that SAK confidentiality is maintained under uncompromised CAK conditions (fulfilling \textbf{SR3}).

\subsubsection{Session Ordering and Transition Integrity}
Ordering lemmas enforce state-machine flow rules, preventing out-of-order execution or state rollback.

\paragraph{Pre-Rekey Ordering.} The lemma \texttt{rekey\_cannot\_start\_}\allowbreak\texttt{before\_initial\_completion} asserts that a Key Server cannot initiate a rekey round ($\mathtt{RekeyStarted}$) at time $i$ unless an initial session has already been completed at time $j < i$.

\paragraph{Rekey Completion Ordering (\texttt{rekey\_after\_initial\_completion}).} Asserts that a rekey session cannot complete at time $i$ without a prior initial session completion at time $j < i$. Together, these two \texttt{all-traces} lemmas confirm that protocol execution is strictly sequential (fulfilling \textbf{SR4}).

\subsubsection{Key Monotonicity and Rekey Freshness}
Freshness lemmas ensure that key updates produce distinct, un-reused cryptographic keys bound to advancing sequence numbers.

\paragraph{Key Update Lemma (\texttt{key\_update}).} Proves that for any execution trace containing an initial session completion at time $i$ and a rekey completion at time $j$, the rekeyed key $\mathit{sak2}$ is strictly non-identical to the initial key $\mathit{sak1}$ ($\neg(\mathit{sak1} = \mathit{sak2})$).

\paragraph{Key Number Progress (\texttt{key\_number\_progress}).} Confirms counter monotonicity by proving that the Key Number of a rekeyed session ($\mathit{kn1}$) is equal to the successor count of the initial Key Number ($\mathit{kn1} = \mathtt{count}(\mathit{kn})$).

\paragraph{Fresh Rekey Key (\texttt{fresh\_rekey\_key}).} Ensures key freshness by verifying that a rekeyed SAK ($\mathit{sak2}$) accepted in a rekey session could never have been distributed as a valid key in any initial session. These lemmas collectively satisfy \textbf{SR5} and \textbf{SR6}.

\subsubsection{KDF-Bypass and Malicious Key Server Acceptance}
To probe the trust boundary of the protocol (\textbf{SR7}), we evaluate two \texttt{exists-trace} lemmas using the \texttt{Malicious\_KeyServer\_Send} rule.

\paragraph{KDF Bypass Lemma (\texttt{server\_only\_accepts\_kdf\_keys}).} Evaluates whether there exists a trace where the Server accepts a key ($\mathtt{ServerAcceptedSAK}(\mathit{sak})$) that was never generated via the standard KDF path ($\mathtt{KDFGeneratedSAK}(\mathit{sak})$).

\paragraph{Malicious SAK Acceptance Lemma (\texttt{accepts\_non\_kdf\_sak}).} Synthesizes an explicit attack trace where a malicious Key Server generates an arbitrary key $\widetilde{\mathit{fakeSAK}}$ and embeds it in a well-formed MKAPDU:
\begin{align*}
\exists \, \mathit{sak}, i, j. \, \mathtt{MaliciousSAKSent}(\mathit{sak})@i \land \mathtt{ServerAcceptedSAK}(\mathit{sak})@j \land i < j
\end{align*}
Tamarin finds a valid trace for both lemmas, confirming that non-KDF key acceptance is achievable in the model. Listing~\ref{lst:malicious} shows the Tamarin source for these two critical components.

\begin{lstlisting}[caption={Malicious Key Server rule and KDF-bypass existence lemma in Tamarin syntax.},label={lst:malicious}]
rule Malicious_KeyServer_Send:
  let kek  = kdf(~cak,'KEK')
      ick  = kdf(~cak,'ICK')
      mn_ks  = genMN($Keyserver)
      mn_ks1 = count(mn_ks)
      c1   = senc(~fakeSAK, kek)
      icv1 = mac(<$Keyserver,mn_ks1,~kn,c1>, ick)
  in
  [ !SharedCAK(~cak), Fr(~fakeSAK), Fr(~kn) ]
  --[ MaliciousSAKSent(~fakeSAK) ]->
  [ Out(<$Keyserver,mn_ks1,~kn,c1,icv1>) ]

lemma accepts_non_kdf_sak: exists-trace
"Ex sak #i #j.
    MaliciousSAKSent(sak)@i
  & ServerAcceptedSAK(sak)@j
  & #i < #j"
\end{lstlisting}

\subsection{Structural Weakness: KDF-Bypass Attack}
\label{sec:weakness}

\begin{definition}[Malicious SAK Acceptance]
There exists a trace in which \texttt{MaliciousSAKSent}($sak$) is observed before \texttt{ServerAcceptedSAK}($sak$), and $sak$ was never output by \texttt{KDFGeneratedSAK}.
\end{definition}

This exists-trace lemma captures the scenario in which a Key Server holding the CAK injects a fresh but non-KDF-derived SAK into a well-formed MKAPDU. The concrete attack trace proceeds as follows:

\begin{enumerate}
  \item The malicious Key Server, possessing the shared CAK, derives the operational sub-keys $\mathit{kek} = \mathtt{kdf}(\mathit{cak}, \texttt{'KEK'})$ and $\mathit{ick} = \mathtt{kdf}(\mathit{cak}, \texttt{'ICK'})$.
  \item Instead of computing a SAK via the prescribed KDF path ($\mathtt{kdf}(\mathit{cak}, \langle \$\mathit{KS}, \mathit{kn}, \mathit{nonce}\rangle)$), it generates an arbitrary fresh value $\widetilde{\mathit{fakeSAK}}$.
  \item It encrypts the arbitrary key under the shared KEK: $\mathit{c} = \mathtt{senc}(\widetilde{\mathit{fakeSAK}}, \mathit{kek})$.
  \item It computes a valid ICV over the MKAPDU fields using the shared ICK: $\mathit{icv} = \mathtt{mac}(\langle \$\mathit{KS}, \mathit{mn}, \mathit{kn}, \mathit{c}\rangle, \mathit{ick})$.
  \item The Server receives the MKAPDU, verifies the ICV (which succeeds because the ICK is correctly derived from the shared CAK), validates the MN counter, and decrypts $\widetilde{\mathit{fakeSAK}}$ from the ciphertext.
  \item The Server accepts $\widetilde{\mathit{fakeSAK}}$ as the session key, with no mechanism to detect that it was not derived via the prescribed KDF path.
\end{enumerate}

\paragraph{Practical impact.} A Key Server that chooses the SAK gains complete control over the data-plane encryption key. Since MACsec uses the SAK for symmetric authenticated encryption of Ethernet frames, an adversary who selected the SAK value can:
\begin{itemize}
  \item Decrypt all traffic protected under that SAK (passive eavesdropping).
  \item Inject or modify MACsec-protected frames (active attacks).
  \item Share the chosen SAK with a third party, enabling a relay or wiretap without the Server's knowledge.
\end{itemize}

\paragraph{Root cause and mitigations.} The weakness arises because the MKAPDU authentication (via the ICV) guarantees that the sender possesses the CAK, but does not bind the SAK payload to the prescribed derivation path. Potential mitigations include:
\begin{itemize}
  \item \textbf{KDF proof-of-compliance:} The Key Server could include the KDF inputs (Key Number, nonce) in a verifiable form, allowing the Server to independently re-derive and compare the SAK. However, this requires the Server to have access to the KDF nonce, which is not currently transmitted in the clear.
  \item \textbf{Mutual key derivation:} Both parties could contribute entropy to the SAK derivation (e.g., via a Diffie--Hellman-like exchange or by each providing a nonce), ensuring no single party controls the key value. This approach would require protocol-level changes to IEEE 802.1X.
  \item \textbf{Key confirmation:} A post-distribution key-confirmation step in which both parties demonstrate knowledge of the SAK through a challenge--response mechanism could detect mismatches, although it would not prevent a malicious Key Server from knowing the key it injected.
\end{itemize}

This is a \emph{structural} property of the protocol rather than a cryptographic break: all cryptographic primitives function correctly, but the protocol's trust model implicitly assumes that the Key Server is honest.

\subsection{Gap between IEEE 802.1X-2020 and our model}

While our Tamarin model successfully verifies MKA under a standard Dolev-Yao adversary, the model necessarily abstracts away several operational details present in the IEEE 802.1X-2020 standard. The primary gaps include:
\begin{itemize}
    \item \textbf{Keyserver Selection:} We omit the keyserver selection process and assume the keyserver is already selected. This assumption is valid for our model because we are primarily concerned with the security of the key agreement protocol itself, not the keyserver discovery process. 
    \item \textbf{Detailed State Machines:} IEEE 802.1X-2020 specifies comprehensive finite-state machines for key generation, SA activation, and session state transitions. Our model captures the high-level logic (initiation, key exchange, rekeying) but omits low-level transitions like timers, retry counts, and error states.
    \item \textbf{Message Numbering:} The IEEE 802.1X-2020 standard specifies a message numbering scheme for MKAPDU messages. We assumed that both participants already send MKAPDUs; therefore, they know all participants' message numbers and can compare new message numbers with previous ones. This assumption is valid in our model because we assume that both participants have already exchanged MKAPDUs and know each other's message numbers.
\end{itemize}

\subsection{Verification Summary}

The verification confirms that MKA provides the expected security guarantees when the long-term CAK is uncompromised. Specifically: (i)~the model is executable and free of logical deadlocks (SR1); (ii)~the Key Server and Server achieve mutual agreement on session parameters (SR2); (iii)~SAKs remain confidential under the Dolev--Yao adversary (SR3); (iv)~session ordering is strictly sequential (SR4); and (v)~rekeyed keys are fresh, distinct, and bound to monotonically advancing counters (SR5, SR6).

The most significant finding is the existence of an attack trace confirming the KDF-bypass weakness described in Section~\ref{sec:weakness} (SR7). A malicious Key Server holding the CAK can construct a well-formed MKAPDU carrying an arbitrary fresh SAK. Because the MAC is computed with the ICK derived from the shared CAK, the Server accepts the message and records the injected SAK as valid. This result exposes a structural limitation in the protocol's trust model: the Server has no independent proof that the SAK was generated through the prescribed KDF path.
